# Роадмап: собственный OIDC SSO для Twenty CRM (форк)

Статус: фазы 0-6 и задачи A, B выполнены и смержены в `main`. Фаза 7 (закрытие): синхронизация с upstream выполнена, блокер снят (раздел 9). Документация пользователя (RU и EN) лежит в `docs/oidc-sso/`, README модуля с реестром швов в каталоге модуля. Итоговая приёмка отложена. Проход по UI в браузере выполнен на образе `main`; скрытие карточки апгрейда старого SSO (шов S4) проверено отдельно в браузере через dev-сервер фронта, в образ оно попадёт после пересборки. Версия 11.

## 1. Цель и рамки

Заменить Enterprise-реализацию OIDC (файлы с `/* @license Enterprise */`) собственной, написанной независимо: вход через корпоративный IdP, настройка провайдеров администратором воркспейса, несколько провайдеров на воркспейс.

В скоупе: только OIDC (Authorization Code + PKCE). Миграция данных из старой таблицы не нужна.
Вне скоупа: SAML, SCIM, маппинг групп и ролей, back-channel logout, режим «только SSO» для домена, ротация секрета из UI.

Главное инженерное требование: **минимальный diff относительно upstream**, чтобы синхронизация форка (`git merge upstream/main`) оставалась дешёвой.

Принципы кода: данные отдельно от логики (чистые функции), один сервис с IO, один контроллер, без passport-стратегий и динамических фабрик.

## 2. Юридические условия

- Clean-room: Enterprise-файлы не копировать и не править. Реализация по спецификациям (RFC 6749, RFC 7636, OIDC Core).
- Новые имена модулей, таблиц и файлов, без маркера `@license Enterprise`.
- Решение заказчика: старый Enterprise-модуль остаётся в дереве подключённым, но недостижимым без лицензионного ключа, и это считается допустимым. Стратегия 3.2 принята окончательно, вариант 3.7-Б не рассматривается.
- Это не юридическая консультация.

### 3.2 Принятая стратегия: параллельный аддитивный модуль

1. **Старый Enterprise-модуль не трогаем вообще.** Ни удалений, ни правок: нет конфликтов modify/delete, схема БД и миграции upstream остаются согласованными (старая таблица и сущность остаются, TypeORM подбирает сущности глобом `core-modules/**/*.entity.ts`, отдельной регистрации не нужно).
2. **Новый код только в новых путях**, ничего из них upstream не создаст:
   - сервер: `packages/twenty-server/src/engine/core-modules/oidc-sso/` (сущность подхватывается глобом автоматически, без правок datasource);
   - фронт: `packages/twenty-front/src/modules/oidc-sso/`;
   - миграция: новый файл (раздел 3.5);
   - документы: `docs/oidc-sso-roadmap.md`.
3. **Нет пересечений имён с upstream**, чтобы старый и новый модули жили вместе: таблица `workspaceOidcProvider`; GraphQL-типы, мутации и запросы с префиксом `Oidc` (например `createOidcProvider`, `oidcProviders`), которых нет в старой схеме; маршруты `/auth/oidc-sso/login/:id` и `/auth/oidc-sso/callback` вместо `/auth/oidc/*`. Поэтому старые enum `IdentityProviderType` и `SSOIdentityProviderStatus` мы не переопределяем и не используем.
4. **Своя публичная часть вместо переиспользования `authProviders.sso`.** Список провайдеров для экрана входа отдаёт наш собственный публичный запрос по воркспейсу. Не правим `workspace.entity.ts`, `get-auth-providers-by-workspace.util.ts`, `public-workspace-data.dto.ts`, `user-workspace.service.ts`, `workspace-domains.service.ts`, `approved-access-domain.service.ts`, `auth.resolver.ts`, `available-workspaces.dto.ts`, `list-and-delete-orphaned-workspace-entities.command.ts`.
5. **Каскадное удаление без правок.** Сущность наследует `WorkspaceRelatedEntity` (`onDelete: 'CASCADE'`), поэтому при удалении воркспейса наши строки удаляются сами.
6. **Фронт без codegen.** Файл `generated-metadata/graphql.ts` отслеживается и разрастается при каждой правке схемы, поэтому каждая синхронизация конфликтовала бы в нём. Свои gql-документы пишем вручную с локальными типами результата и не запускаем `graphql:generate` в коммите.
7. **Lingui.** Строки через `t`/`msg`, каталоги переводов не коммитим (правило репозитория).

### 3.4 Процедура синхронизации и защита от дрейфа

- Один раз: `git remote add upstream https://github.com/twentyhq/twenty.git` (сейчас настроен только `origin` = ваш форк).
- Включить `git config rerere.enabled true`.
- Швы S1–S6 держим отдельными небольшими коммитами с префиксом `fork(oidc-sso):`, остальное в одном каталоге-наборе коммитов `feat(oidc-sso):`. Синхронизация: `git merge upstream/main` (не rebase, чтобы не переписывать историю форка).
- Скрипт `scripts/fork/check-oidc-seams.sh` (в новом каталоге, без правок upstream): падает, если `git diff --name-only upstream/main...HEAD` содержит файл вне `oidc-sso/`-путей и вне разрешённого списка швов. Запускать локально и в CI форка.
- После каждой синхронизации: типы (`tsgo`), unit-тесты модуля, smoke-вход через Keycloak/Dex.

### 3.5 Миграция БД

Генератор `database:migrate:generate` не используем: он кладёт команду в папку версии upstream и дописывает её в `instance-commands.constant.ts`, а этот файл самый горячий в репозитории (201 коммит за 6 месяцев).

Вместо этого команда пишется вручную **внутри `oidc-sso/`** и объявляется провайдером нашего модуля. Реестр команд (`UpgradeCommandRegistryService`) находит их через `DiscoveryService` по декоратору `@RegisteredInstanceCommand(version, timestamp)` среди всех провайдеров приложения, а CLI-приложение (`CommandModule`) импортирует `AppModule`, поэтому наш модуль в него попадает. Правок файлов upstream нет.

Условия:
- Версия в декораторе жёстко `'2.51.0'` (текущая на момент написания). Не импортировать `TWENTY_CURRENT_VERSION`: имя команды включает версию, и после её смены команда исполнилась бы повторно.
- SQL идемпотентный (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`), `down` удаляет таблицу.
- Timestamp реальный (epoch-ms) и больше всех в папке версии `2.51.0` на момент создания.
- Если upstream уберёт версию из `TWENTY_ALL_VERSIONS`, тип `TwentyAllVersion` перестанет компилироваться: это явный сигнал. Тогда перерегистрировать команду под текущей версией (идемпотентность делает повтор безопасным). Без этого свежая установка не создала бы таблицу.
- Проверка в Фазе 1 (выполнена): на пустой БД команда обнаруживается реестром и создаёт таблицу, `generate:instance-command` сообщает об отсутствии дрейфа схемы (ограничения объявлены в сущности через `@Unique` и `@Check`, имена PK/FK посчитаны функциями TypeORM), повторный запуск пропускает команду по имени, `down` и повторный `up` работают.
- Побочный эффект: если команда исполняется на инстансе, где 2.51.0 уже полностью применена, команда `upgrade` один раз прогонит workspace-команду 2.51.0 заново (она идемпотентна, проверено на двух воркспейсах без ошибок).

Исполнение на уже пройденной версии. `upgrade` идёт от курсора (последняя выполненная команда любого вида) и не видит инстанс-команду, добавленную в версию, которую база уже закончила: она остаётся левее курсора при любом типе (fast или slow) и любом timestamp. Такую команду исполняет `run-instance-commands`: она ищет невыполненные команды по имени, без курсора. Поэтому entrypoint образа (шов S8) вызывает её после `upgrade`, а ошибка не рвёт старт. Проверено на копии БД Zirek (2.54.0, уже дошедшей до 2.56.0): `upgrade` таблицу не создаёт, затем `run-instance-commands` создаёт её, повторный запуск команду пропускает. Условия: сервер не отключает миграции (`DISABLE_DB_MIGRATIONS` не `true`; воркер отключает их по умолчанию, так что на старте запускается только сервер), исполняются только fast-команды (команда форка должна оставаться fast), а сама `run-instance-commands` отказывается работать, пока воркспейсы не закончили предыдущую версию. Сам скрипт entrypoint проверен на заглушках, целиком в контейнере не запускался.

### 3.6 Цена изоляции (потерянные функции)

Так как мы не правим сквозные места, наши провайдеры не участвуют в:
- выборе воркспейса на многотенантном экране входа (`availableWorkspaces.sso`);
- SSO-маршрутизации по подтверждённому домену (`approvedAccessDomain`);
- общем списке `authProviders.sso` на публичных данных воркспейса.

Вход по ссылке воркспейса (поддомен или кастомный домен) работает полностью. Решение заказчика: выбор воркспейса на общем экране входа и SSO по домену не нужны и не планируются (неавторизованный пользователь не должен узнавать, какие воркспейсы существуют, см. раздел 8). Общий список `authProviders.sso` в публичных данных воркспейса остаётся сознательным разменом: вход по ссылке воркспейса работает без неё, при необходимости её можно добавить одним швом.

### 3.7 Варианты, которые отвергнуты

- **А. Заменять Enterprise-модуль (версия 1 плана):** 14 файлов в зоне конфликтов.
- **Б. Удалить Enterprise-файлы из форка:** юридически чище, но каждое изменение upstream в этих файлах превращается в конфликт modify/delete на каждой синхронизации. Возвращаться к этому варианту только по решению юриста.
- **В. Переиспользовать старую таблицу и сущность:** требует загружать Enterprise-код в работе и тянет конфликты схемы.

## 4. Результаты статической проверки допущений

Проверено чтением кода (без запуска). Подтверждено:
- `AuthService` публично даёт всё для входа, но **не экспортируется** из `AuthModule` (шов S2).
- Для провайдера `SSO` нет переключателя на воркспейс (`workspaceValidator.isAuthEnabledOrThrow` всегда пропускает).
- Сессии: `express-session` + Redis, cookie `lax`, `httpOnly`, 30 минут. Callback от IdP это top-level GET, поэтому state/nonce/PKCE можно хранить в сессии. Условия: только `response_mode=query`, явный `session.save()` перед редиректом.
- `SecureHttpClientService.getSsrfSafeAgent` создан для `openid-client`; зависимость `openid-client ^5.7.0` уже есть.
- Сущности регистрируются глобом `core-modules/**/*.entity.ts` (без правок datasource для новой, и без возможности исключить старую без правки).

Риски (учтены в фазах):
1. Шифрование секрета: `encrypt` это AES-CTR без целостности. Нужны `encryptVersioned` / `decryptVersionedOrThrow` (enc:v2) и регистрация колонки в реестре ротации ключей `database/commands/secret-encryption-rotation/`. Реестр центральный (подтверждено), это шов S3.
2. Утечка между воркспейсами: при `workspaceInviteHash` поиск воркспейса игнорирует `workspaceId`. Жёсткая сверка `workspace.id === provider.workspaceId` обязательна и покрывается тестом.
3. Было не проверено, теперь проверено: `openid-client` 5.7.0 установлен, `callback()` сам сверяет `state`, `nonce`, `iss`, подпись id_token и PKCE; правило обнаружения резолверов `include` в `@nestjs/graphql` подтверждено по исходникам библиотеки (рекурсивно по `imports`), запуском оно подтвердится в Фазе 5, когда появятся резолверы; `session.save()` перед редиректом на `connect-redis` работает (смоук-тест Фазы 3). Осталось зависимым от IdP: отдача `email_verified` (с задачи A вход требует явного `true`, Azure AD без этого claim не поддерживается) и наличие email в id_token (Azure AD v2 не кладёт, есть fallback на userinfo, на реальном Azure не проверялся).

### Верификация архитектуры (чтением кода)

Подтверждено:
- Сущности подхватываются глобом, отдельной регистрации не нужно.
- Каскад по `workspaceId` даёт `WorkspaceRelatedEntity` (`onDelete: 'CASCADE'`); список в `list-and-delete-orphaned-workspace-entities.command.ts` только диагностический, тестов-принуждений к нему нет.
- Резолверы разделены по схемам декоратором `@MetadataResolver()`, схема строится по достижимым типам (патч `@nestjs/graphql`), поэтому наши типы с префиксом `Oidc` не пересекутся со старыми.
- Маршрут `/auth/oidc-sso/*` нигде не зашит в upstream (в коде встречаются только старые `/auth/oidc/*` и `/auth/saml/*`).
- `getAuthProvidersByWorkspace` вызывается один раз (`workspace.resolver.ts:488`); мы его не используем.

Исправлено по итогам проверки: шов на реестр ротации стал обязательным (S3); фронтовая видимость SSO размазана по нескольким файлам (S5–S6), а не по одному; Enterprise-хук `useSso` обращается к старой мутации `getAuthorizationUrlForSSO` и для наших id не работает, его нужно заменить нашим.

### Отдельная задача A. Подтверждённый email обязателен (выполнена, PR #10)
Источник: code-review PR #6, открытый вопрос о `email_verified`. Решено без флага, колонки и миграции: `OidcAccountService.signIn` входит с `isEmailAlreadyVerified: true`, поэтому `extractOidcIdentity` для всех провайдеров пропускает только `email` с явным `email_verified === true` (булево или строка `'true'` в любом регистре).
- Email из `upn` больше не принимается: у него нет признака подтверждения.
- Цена: IdP без `email_verified` (Azure AD, если claim нет ни в id_token, ни в userinfo) не поддерживается. Если `email` есть в id_token без `email_verified`, userinfo не опрашивается и вход отклоняется. Вернуть мягкий режим можно отдельной задачей с флагом провайдера (колонка и миграция).

### Отдельная задача B. Аутентификация клиента `client_secret_post` (выполнена)
Источник: решение заказчика по вопросу о `client_secret_post` (раздел 8). Проверка показала, что отдельный код не нужен: `openid-client` сам выбирает `client_secret_post`, когда клиент создан без явного `token_endpoint_auth_method`, а IdP в `token_endpoint_auth_methods_supported` не перечисляет `client_secret_basic`, но перечисляет `client_secret_post`. Наш `buildClient` метод не задаёт, поэтому поддержка работала с Фазы 3, а формулировка «только `client_secret_basic`» в статусе Фазы 3 была ошибкой.
- Результат: тесты в `oidc-protocol.service.spec.ts` фиксируют метод аутентификации, который получает клиент: `client_secret_basic` при отсутствии списка, пустом списке, списке с basic и при обоих методах; `client_secret_post` только когда IdP перечисляет лишь его.
- Проверка запроса: `callback` в тестах подменён, поэтому фактическую отправку секрета проверяет `scripts/fork/oidc-dev/check-client-auth-method.cjs` (падает при расхождении).
- Не покрыто: IdP, который перечисляет оба метода, но реально принимает только post. Лечится только явным выбором метода в настройках провайдера (колонка и миграция); делать при появлении такого IdP.
- Ограничение проверки: mock IdP не публикует список методов, поэтому сквозной проверки на живом сервере нет, только уровень `openid-client` и юнит-тесты.

## 7. Чек-лист приёмки

Функциональное соответствие Enterprise-версии (с учётом раздела 3.6):
- несколько IdP на воркспейс; статусы Active / Inactive / Error;
- Authorization Code + PKCE S256, scope `openid email profile`;
- email из `email` (только с `email_verified=true`, строка в любом регистре), имя из `given_name` / `family_name`;
- вход по приглашению, кастомные домены, ошибки редиректом на `/verify`;
- connected account с claims (за существующим feature flag);
- SSRF-защита запросов к IdP.

Сценарии: новый пользователь; существующий; вход по инвайту; неактивный провайдер; неверный и повторно использованный `state`; `email_verified` равен `false` или отсутствует; email только в `upn`; IdP во внутренней сети (блокируется); провайдер чужого воркспейса и подмена через `workspaceInviteHash`; регресс входа по паролю, Google и Microsoft; старый модуль не мешает (нет конфликтов имён).

Улучшения относительно Enterprise: зашифрованный секрет, одноразовые `state` и `nonce`, проверка `email_verified`, кэш discovery, отсутствие Enterprise- и billing-гардов.

## 9. Синхронизация с upstream (выполнена 2026-11-05)

Слияние `upstream/main` (`1a860b238a`) лежит в ветке `fork/oidc-sso-upstream-sync`. Первая пробная попытка (673 коммита) нашла блокер, после его снятия слияние повторено на свежем upstream (ещё 21 коммит).

Что показало слияние:
- Текстовый конфликт был один, в снапшоте эндпоинтов S7. Остальные швы склеились автоматически.
- Блокер: upstream в #29661 удалил `AuthPrincipalGuard` и `SettingsPermissionGuard`, ввёл `AccessPolicyGuard(accessPolicy)` и сменил формат снапшота. Помимо гардов в модуле сломались ещё два импорта: фильтр `PermissionsGraphqlApiExceptionFilter` и `PermissionsModule` переехали в `src/engine/permissions/`.

Что сделано:
- `OidcProviderResolver` перенесён на `AccessPolicyGuard` с теми же принципалами (только обычная пользовательская сессия) и правом `SECURITY`; семантика старой пары гардов сверена по коду. `PermissionsModule` из `OidcSsoModule` убран: `AccessPolicyModule` глобальный.
- Публичный резолвер и контроллер входа менять не пришлось: `PublicEndpointGuard` и `NoPermissionGuard` остались прежними.
- Снапшот S7 регенерирован интеграционным тестом, в нём ровно 7 наших записей. На свежем upstream тест проходит без повторной регенерации.
- Проверено на коммите `070f710688` (слияние upstream `1a860b238a`): `tsgo` без ошибок, 143 unit-теста модуля, тест снапшота S7, админский смоук (24 из 24) и смоук входа (16 из 16) на собранном сервере. UI на этой ветке в браузере не проверялся: проход по UI делался на образе `main`.

Как синхронизироваться в следующий раз: см. раздел «Syncing with upstream» в README модуля. `rerere` помнит резолюцию снапшота «взять upstream», но снапшот всё равно надо регенерировать (остальные нюансы в README модуля).

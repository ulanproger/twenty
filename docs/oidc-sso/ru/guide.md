# OIDC SSO: руководство администратора

Вход в воркспейс Twenty через корпоративный OpenID Connect провайдер (Keycloak, Okta, Auth0, Google и другие). Поддерживается только Authorization Code с PKCE S256. Провайдеры настраиваются отдельно для каждого воркспейса, их может быть несколько. Можно вместо этого задать один провайдер на всю платформу через переменные окружения ([ниже](#один-провайдер-на-всю-платформу)).

Это собственная реализация форка. Старый Enterprise-блок «SSO» на странице безопасности скрыт, если у инстанса нет валидного Enterprise-плана, и к OIDC-провайдерам отношения не имеет.

Дальше: [рецепты для IdP](providers.md), [справочник и диагностика](reference.md).

## Что нужно заранее

- Twenty доступен по постоянному адресу, `SERVER_URL` в окружении сервера совпадает с ним.
- В продакшене IdP работает по `https`. Адрес `http` принимается только при `NODE_ENV=development`.
- IdP умеет PKCE S256 и в id_token отдаёт `email` с `email_verified=true`. Без этого вход невозможен, проверьте по [чек-листу совместимости](providers.md#чек-лист-совместимости).
- У вас есть право Security в воркспейсе (администратор).
- Воркспейс активирован (прошёл онбординг).

## Быстрый старт

1. В IdP создайте приложение типа Web / Confidential с потоком Authorization Code. Redirect URI укажите позже (шаг 3), пока можно любой.
2. Запишите Issuer, Client ID и Client secret.
3. В Twenty откройте Settings, Security. В карточке «OIDC» нажмите «Add OIDC provider». В диалоге сверху показан redirect URI вида `https://<ваш-адрес>/auth/oidc-sso/callback`. Скопируйте его и добавьте в список разрешённых redirect URI в IdP.
4. Заполните поля Name (это текст кнопки входа), Issuer URL, Client ID, Client secret и нажмите «Add». Twenty при сохранении сам скачивает конфигурацию IdP и проверяет её. Если IdP недоступен или конфигурация не подходит, провайдер не создаётся и показывается ошибка.
5. Выйдите и откройте страницу входа воркспейса. Должна появиться кнопка «Sign in with <Name>». Нажмите её и войдите.

Секрет клиента шифруется и обратно в интерфейс и API не возвращается.

## Как проходит вход

1. Пользователь открывает адрес воркспейса и нажимает «Sign in with <Name>».
2. Браузер идёт на `/auth/oidc-sso/login/<id провайдера>`. Сервер создаёт одноразовые `state`, `nonce` и PKCE-проверку и отправляет браузер в IdP.
3. Пользователь входит в IdP.
4. IdP возвращает браузер на `/auth/oidc-sso/callback`. Сервер обменивает код на токены и проверяет подпись и `nonce` id_token.
5. Из id_token берутся email (обязателен, только с `email_verified=true`), имя из `given_name` и `family_name`.
6. Пользователь входит в воркспейс. Любая ошибка завершает вход редиректом на страницу `/verify` с сообщением.

Незавершённый вход живёт 10 минут и используется один раз. Повтор callback, чужой или просроченный `state` отклоняются.

## Кто может войти

- Существующий участник воркспейса с тем же email: входит.
- Новый пользователь: входит только по приглашению. Откройте ссылку-приглашение воркспейса, затем нажмите кнопку входа: идентификатор приглашения (`workspaceInviteHash`) передаётся дальше автоматически. Если включена публичная ссылка-приглашение, подойдёт она.
- Новый пользователь без приглашения получает «User does not have access to this workspace».
- Пока воркспейс не активирован, вход новых пользователей даёт «Workspace is not ready to welcome new members».

Доверие к IdP задаёт администратор: ограничения по домену email для провайдера нет. Если нужно ограничить круг людей, делайте это на стороне IdP.

## Управление провайдерами

В карточке OIDC у каждой строки есть меню:

- Deactivate / Activate: неактивный провайдер пропадает с экрана входа, вход через него отклоняется. Данные сохраняются.
- Delete: после подтверждения удаляет провайдера, пользователи больше не смогут войти через него.

Можно добавить несколько провайдеров, на экране входа будет по кнопке на каждый. Один и тот же Issuer с одним и тем же Client ID добавить дважды нельзя.

## Один провайдер на всю платформу

Если на инстансе один корпоративный IdP для всех воркспейсов, задайте его в окружении сервера:

```
OIDC_ISSUER=https://idp.example.com/auth/v1
OIDC_CLIENT_ID=twenty
OIDC_CLIENT_SECRET=...
OIDC_NAME=Корпоративный вход   # необязательно, по умолчанию «OIDC»
```

- В IdP достаточно одного клиента и одного redirect URI: `https://<ваш-адрес>/auth/oidc-sso/callback`.
- Провайдер включается, только когда заданы Issuer, Client ID и Client secret, а Issuer корректен (в продакшене `https`). Иначе всё работает как раньше, в логе будет предупреждение.
- Пока он включён, на странице входа каждого воркспейса одна кнопка с именем `OIDC_NAME`, а настройка провайдеров по воркспейсам отключена: в Settings, Security он показан только для чтения, создание, изменение и удаление отклоняются.
- Ранее созданные провайдеры воркспейсов не удаляются, но не используются. Если убрать переменные, они снова заработают.
- Провайдер доступен во всех воркспейсах инстанса: отдельного включения для воркспейса нет (флага SSO у воркспейса не существует). Единственная проверка на воркспейсе: участник, приглашение или одобренный домен email. Правила доступа те же: новый пользователь входит только по приглашению, `email_verified` обязателен. Секрет берётся из окружения и в интерфейс не попадает.
- Переменные читаются при каждом запросе, но менять окружение сервера обычно значит перезапуск контейнера.

## Чего сейчас нет

- Редактирование Issuer, Client ID и секрета. Чтобы сменить, удалите провайдера и создайте заново. Переименовать и включать или выключать можно через API ([справочник](reference.md#graphql-api)).
- Выбора воркспейса на общем экране входа и SSO по домену email. Входить нужно с адреса воркспейса: так посторонний не узнаёт, какие воркспейсы существуют.
- Режима «только SSO» и запрета входа по паролю для воркспейса.
- Статуса «Error» у провайдера, только Active и Inactive.
- Провайдеров без `email_verified` (например, Microsoft Entra ID).
- SAML, SCIM, сопоставления групп и ролей.

## Частые вопросы

**Кнопка входа не появилась.** Провайдер должен быть Active, а страница открыта с адреса именно этого воркспейса.

**Вход заканчивается «Single sign-on authentication failed».** Это общий текст, причина записана в логе сервера. См. [диагностику](reference.md#диагностика).

**Можно ли пользоваться паролем и SSO одновременно?** Да, вход по паролю остаётся как был.
